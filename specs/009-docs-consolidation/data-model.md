# Phase 1: Data Model & Entities

**Feature**: Documentation Consolidation and Reorganization
**Date**: 2025-11-10
**Status**: Complete

## Overview

This document defines the logical data model for the documentation consolidation system. While this is a documentation-only feature (no executable code), the "data model" represents the structure and relationships of documentation metadata, file organization, and validation rules.

## Core Entities

### 1. DocumentationFile

Represents a single Markdown documentation file with metadata.

**Attributes**:

- `path` (string, required): Relative path from repository root (e.g., `docs/patterns/profile-management.md`)
- `title` (string, required): Human-readable title from frontmatter
- `version` (SemanticVersion, required): Document version (e.g., `1.2.0`)
- `created` (ISO8601Date, required): Creation date
- `lastUpdated` (ISO8601Date, required): Last modification date
- `status` (DocumentStatus, required): One of `current`, `deprecated`, `draft`
- `tags` (string[], required): Categorization tags (e.g., `["architecture", "mvvm"]`)
- `related` (RelativePath[], optional): Links to related documentation
- `supersedes` (RelativePath, optional): Link to deprecated predecessor
- `contentHash` (MD5Hash, optional): Hash of file content for duplicate detection

**Validation Rules**:

- Path must use forward slashes and be relative to repository root
- Version must follow semantic versioning format (MAJOR.MINOR.PATCH)
- Created date must not be in the future
- LastUpdated must be >= created date
- Status must be one of the allowed enum values
- Tags must be non-empty array
- Related paths must exist in the documentation tree
- Supersedes path must exist and have status=deprecated

**State Transitions**:

```
draft → current       (on initial publication)
current → deprecated  (when superseded by newer version)
deprecated → removed  (after retention period, typically 2 years)
```

**Example**:

```yaml
---
title: "Profile Management Pattern"
version: "2.1.0"
created: "2025-01-15"
last-updated: "2025-11-10"
status: "current"
tags: ["patterns", "profile-management", "reactive"]
related:
  - docs/patterns/internal-method.md
  - docs/architecture/clean-architecture.md
supersedes: docs/archive/old-profile-pattern.md
---
```

### 2. DocumentationCategory

Represents a logical grouping of documentation files.

**Attributes**:

- `name` (string, required): Category name (e.g., `architecture`, `patterns`)
- `path` (RelativePath, required): Directory path (e.g., `docs/architecture/`)
- `description` (string, required): Purpose and content description
- `subcategories` (DocumentationCategory[], optional): Nested categories (max 1 level)
- `indexFile` (RelativePath, required): Path to category index (e.g., `_index.md`)
- `fileCount` (integer, computed): Number of files in this category
- `depth` (integer, computed): Depth in hierarchy (root=0, max=2)

**Validation Rules**:

- Name must be kebab-case (lowercase with hyphens)
- Path must match pattern `docs/{category}/` or `docs/{category}/{subcategory}/`
- Depth must not exceed 2 (max 3 levels total including root)
- Index file must exist and contain category overview

**Defined Categories**:

| Name | Path | Description | Max Depth |
|------|------|-------------|-----------|
| `architecture` | `docs/architecture/` | System architecture and design decisions | 1 (has `decisions/` subcategory) |
| `patterns` | `docs/patterns/` | Implementation patterns and best practices | 1 (has `examples/` subcategory) |
| `guides` | `docs/guides/` | Developer guides and workflows | 1 (has `migration/` subcategory) |
| `templates` | `docs/templates/` | Code and documentation templates | 1 (has `ui-integration/` subcategory) |
| `reviews` | `docs/reviews/` | Code reviews and quality reports | 1 (has `archive/` subcategory) |
| `archive` | `docs/archive/` | Deprecated documentation | 0 (flat, no subcategories) |

### 3. CrossReference

Represents a bidirectional relationship between documentation files.

**Attributes**:

- `sourceFile` (RelativePath, required): File containing the reference
- `targetFile` (RelativePath, required): File being referenced
- `linkType` (LinkType, required): Type of relationship
- `context` (string, optional): Surrounding text/reason for link
- `isAutoGenerated` (boolean, required): True if generated by script, false if manual

**Link Types**:

- `implements`: Source implements pattern/architecture described in target
- `supersedes`: Source replaces target (target should be deprecated)
- `relates-to`: General related content
- `migrates-from`: Migration guide linking old to new approach
- `example-of`: Source is example implementation of target pattern
- `references`: General reference without specific relationship type

**Validation Rules**:

- Source and target files must exist
- Bidirectional links should be symmetric (if A relates-to B, B should relate-to A)
- Supersedes links require target status=deprecated
- Example-of links require target to be in `patterns/` category

**Relationship Graph**:

The system maintains an in-memory graph of all cross-references for:

- Orphan detection (files with no incoming links)
- Related documentation section generation
- Impact analysis (what's affected if a file is deprecated)

### 4. MigrationMapping

Represents the mapping from old file location to new consolidated location.

**Attributes**:

- `oldPath` (RelativePath, required): Original file path (e.g., `.copilot-tracking/memory-bank/systemPatterns.md`)
- `newPath` (RelativePath, required): New consolidated path (e.g., `docs/patterns/system-patterns.md`)
- `migrationDate` (ISO8601Date, required): Date of migration
- `redirectStubCreated` (boolean, required): Whether redirect stub was created at old location
- `stubRemovalDate` (ISO8601Date, optional): When redirect stub will be removed (typically +3 months)
- `gitHistoryPreserved` (boolean, required): Whether git mv was used
- `wasDeduplicatedWith` (RelativePath[], optional): Other files merged into this one

**Validation Rules**:

- Old path must not equal new path
- Old path must be outside `docs/` directory
- New path must be inside `docs/` directory
- If redirectStubCreated=true, stubRemovalDate must be set
- StubRemovalDate must be >= migrationDate + 90 days (3 months minimum)

**Example**:

```json
{
  "oldPath": ".copilot-tracking/memory-bank/systemPatterns.md",
  "newPath": "docs/patterns/system-patterns.md",
  "migrationDate": "2025-11-15",
  "redirectStubCreated": true,
  "stubRemovalDate": "2026-02-15",
  "gitHistoryPreserved": true,
  "wasDeduplicatedWith": [
    ".copilot-tracking/archive/old-patterns.md",
    "docs/old/patterns-backup.md"
  ]
}
```

### 5. ValidationRule

Represents an automated validation check for documentation quality.

**Attributes**:

- `ruleId` (string, required): Unique identifier (e.g., `LINK-001`, `META-002`)
- `name` (string, required): Human-readable name
- `description` (string, required): What the rule checks
- `severity` (Severity, required): `error` (blocking) or `warning` (non-blocking)
- `category` (string, required): `link`, `metadata`, `structure`, `content`
- `enabled` (boolean, required): Whether rule is active

**Severity Levels**:

- **error**: Blocks CI/CD pipeline; must be fixed before merge
- **warning**: Reported but doesn't block; should be addressed eventually

**Defined Rules**:

| Rule ID | Name | Description | Severity | Category |
|---------|------|-------------|----------|----------|
| LINK-001 | Broken Internal Links | All internal links must resolve | error | link |
| LINK-002 | Orphaned Files | Files should have incoming links (except index) | warning | link |
| META-001 | Required Frontmatter | All files must have complete frontmatter | error | metadata |
| META-002 | Valid Version Format | Version must be semver (X.Y.Z) | error | metadata |
| META-003 | Valid Date Format | Dates must be ISO8601 (YYYY-MM-DD) | error | metadata |
| META-004 | Status Enum | Status must be current/deprecated/draft | error | metadata |
| STRUCT-001 | Max Depth Violation | Directory depth must not exceed 3 levels | error | structure |
| STRUCT-002 | Missing Category Index | Each category must have _index.md | error | structure |
| CONTENT-001 | Duplicate Content | Flag files with >80% content similarity | warning | content |
| CONTENT-002 | Outdated References | Flag references to deprecated paths | warning | content |

### 6. ArchiveEntry

Represents a deprecated documentation file that has been archived.

**Attributes**:

- `originalPath` (RelativePath, required): Path before archiving
- `archivePath` (RelativePath, required): Path in archive directory
- `archiveDate` (ISO8601Date, required): When archived
- `removalDate` (ISO8601Date, required): When eligible for permanent deletion (archiveDate + 2 years)
- `deprecationReason` (string, required): Why archived
- `replacement` (RelativePath, optional): Link to superseding documentation
- `preserveIndefinitely` (boolean, required): Override automatic deletion (for historical significance)

**Validation Rules**:

- Archive path must be within `docs/archive/` directory
- Removal date must be >= archive date + 2 years
- If replacement specified, it must exist and have status=current

**Retention Policy**:

- Standard archives: 2 years minimum retention
- Historical significance: Marked with `preserveIndefinitely=true`, never auto-deleted
- Deletion process: Requires manual approval even after retention period

## Entity Relationships

```
DocumentationFile
├─ belongs to → DocumentationCategory
├─ references → DocumentationFile (via CrossReference)
├─ supersedes → DocumentationFile (deprecated)
└─ migrated from → MigrationMapping

DocumentationCategory
├─ contains → DocumentationFile (many)
└─ has parent → DocumentationCategory (optional, max 1 level)

CrossReference
├─ source → DocumentationFile
└─ target → DocumentationFile

ValidationRule
└─ validates → DocumentationFile (many)

ArchiveEntry
├─ original → DocumentationFile (historical)
└─ replacement → DocumentationFile (current)
```

## Data Storage

**Physical Storage**: Filesystem (git repository)

**Metadata Storage**:

- Embedded: YAML frontmatter in each `.md` file
- Generated: JSON manifest files for tooling (e.g., `docs/.metadata/index.json`)
- Version controlled: All metadata committed to git

**Index Files**:

- `docs/INDEX.md`: Master documentation index (human-readable)
- `docs/.metadata/manifest.json`: Machine-readable index for tooling
- `docs/.metadata/cross-references.json`: Generated cross-reference graph
- `docs/.metadata/migration-log.json`: Migration history

## Validation Pipeline Data Flow

```
1. Git Commit
   ↓
2. CI/CD Trigger
   ↓
3. Parse Frontmatter (extract DocumentationFile entities)
   ↓
4. Build Cross-Reference Graph
   ↓
5. Apply ValidationRules
   ↓
6. Generate Reports (violations by severity)
   ↓
7. Gate Decision (block if errors, warn if warnings)
   ↓
8. Update Manifest (if validation passed)
```

## Schema Versioning

The metadata schema itself is versioned and documented:

- **Current Version**: 1.0.0
- **Schema File**: `docs/.metadata/schema.json` (JSON Schema format)
- **Breaking Changes**: Increment MAJOR version, require migration script
- **Backward Compatibility**: Tools must support N-1 schema version during transitions

## Implementation Notes

This data model is implemented through:

1. **Python dataclasses** (for validation scripts)
2. **JSON Schema** (for manifest validation)
3. **YAML Schema** (for frontmatter validation)
4. **Filesystem conventions** (for category structure)

No database required; all data stored as files in git repository with metadata in frontmatter and generated manifest files.
